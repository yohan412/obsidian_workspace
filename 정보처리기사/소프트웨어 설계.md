
## 1.1 요구사항 (Requirements)

소프트웨어가 "무엇을, 어떤 제약 안에서" 해야 하는지 정의하는 단계.

- **기능 요구사항(Functional)**: 시스템이 제공해야 하는 기능·동작.  
    예) "사용자는 로그인할 수 있어야 한다", "주문 내역을 조회한다"
- **비기능 요구사항(Non-functional)**: 기능 외의 품질·제약.  
    성능(응답 1초 이내), 보안, 신뢰성, 사용성, 이식성, 유지보수성 등.

**요구사항 개발 프로세스 (순서 빈출)**  
1. **도출(Elicitation)**: 이해관계자로부터 요구 수집 (인터뷰, 설문, 브레인스토밍, 워크숍, 프로토타이핑, 유스케이스)  
2. **분석(Analysis)**: 요구 충돌·중복 해결, 우선순위 정리, 모델링  
3. **명세(Specification)**: 문서화 (정형 명세 / 비정형 명세)  
4. **확인(Validation)**: 명세가 올바른지 검토·검증 (요구사항 검토, 프로토타이핑, 테스트 설계)

	자주 나오는 함정: "분석" 단계와 "확인" 단계 구분. 분석은 정리, 확인은 검증.

## 1.2 UML (Unified Modeling Language) ★

시스템을 시각적으로 표현하는 표준 모델링 언어.

**3가지 구성요소**: 사물(Things), 관계(Relationship), 다이어그램(Diagram)

**다이어그램 분류 (빈출)**

- **구조적(정적) 다이어그램**: 클래스, 객체, 컴포넌트, 배치(Deployment), 복합체 구조, 패키지
- **행위적(동적) 다이어그램**: 유스케이스, 시퀀스, 커뮤니케이션, 상태(State), 활동(Activity), 타이밍

**관계(Relationship) 6종 ★** — 표기법까지 구분해서 출제됨

## 1.3 디자인 패턴 (GoF 23개) ★★
	 디자인 패턴은 객체 지향 4대 특성(캡슐화, 상속, 추상화, 다형성)과 설계 원칙(SOLID)을 기반으로 구현

- ### 객체지향 4대 특성
![](https://i.imgur.com/Tkl0Fxo.png)


- ### 설계 원칙(SOLID)
	**- S : SRP (단일 책임 원칙)** : "하나의 클래스는 단 하나의 책임(변형의 이유)만 가져야 한다."
	- **설명:** 한 클래스가 데이터 저장, 비즈니스 로직, 이메일 발송 등 여러 일을 맡으면 안 됩니다. 클래스를 수정할 이유는 오직 하나여야 합니다.
    
	- **효과:** 코드 변경 시 영향 범위를 최소화할 수 있습니다.
	**- O : OCP (개방-폐쇄 원칙)**  : "소프트웨어 요소는 확장에는 열려(Open) 있어야 하고, 수정에는 닫혀(Closed) 있어야 한다."
	- **설명:** 새로운 기능을 추가(확장)할 때 기존 코드를 직접 수정하지 않고, 인터페이스나 추상 클래스를 이용해 새로운 클래스를 구현해야 합니다.
    
	- **효과:** 기존 시스템의 안정성을 유지하면서 기능을 손쉽게 확장할 수 있습니다.
	**- L : LSP (리스코프 치환 원칙)**  : "상위 타입의 객체를 하위 타입의 객체로 치환해도 프로그램의 동작이 정상적이어야 한다."
	- **설명:** 자식 클래스는 부모 클래스의 계약(동작 요구사항)을 위반해서는 안 됩니다. 부모 타입으로 동작하는 코드에 자식 인스턴스를 넣어도 예상대로 동작해야 합니다.
    
	- **효과:** 다형성(Polymorphism)의 신뢰성을 보장합니다.
	**- I : ISP (인터페이스 분리 원칙)**  : "클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다."
	- **설명:** 거대하고 범용적인 인터페이스 하나보다, 작고 구체적인 인터페이스 여러 개가 낫습니다. 자신이 사용하지도 않는 메서드를 강제로 구현하지 않도록 인터페이스를 분리합니다.
    
	- **효과:** 불필요한 재의존성 및 리컴파일을 방지합니다.
	**- D : DIP (의존관계 역전 원칙)** : "구체화(Concrete)에 의존하지 말고, 추상화(Abstraction)에 의존해야 한다."
	- **설명:** 고수준 모듈(비즈니스 로직)이 저수준 모듈(세부 구현)을 직접 가리키지 않고, 둘 다 중간의 인터페이스(추상화)에 의존하게 만듭니다.
    
	- **효과:** 외부 라이브러리나 세부 구현 기술이 바뀌어도 핵심 비즈니스 로직에 영향이 미치지 않습니다.

### 생성 패턴(Creational) — 객체 생성 방법을 캡슐화

- **싱글톤(Singleton)**: 클래스의 인스턴스를 단 하나만 생성, 전역 접근점 제공. 예) 설정 관리, 로깅, DB 커넥션 풀
- **팩토리 메서드(Factory Method)**: 객체 생성을 서브클래스에 위임. 어떤 클래스를 만들지 서브클래스가 결정
- **추상 팩토리(Abstract Factory)**: 관련된 객체들의 묶음(군)을 생성하는 인터페이스 제공
- **빌더(Builder)**: 복잡한 객체를 단계별로 생성, 생성 과정과 표현 분리
- **프로토타입(Prototype)**: 기존 객체를 복제(clone)해 새 객체 생성

### 구조 패턴(Structural) — 클래스·객체를 더 큰 구조로 조합

- **어댑터(Adapter)**: 호환되지 않는 인터페이스를 변환해 연결 (변환 어댑터)
- **브리지(Bridge)**: 기능과 구현을 분리해 독립적으로 확장
- **컴포지트(Composite)**: 객체를 트리 구조로 구성, 개별/복합 객체를 동일하게 다룸
- **데코레이터(Decorator)**: 객체에 기능을 동적으로 추가 (상속 대신 위임)
- **퍼사드(Facade)**: 복잡한 서브시스템에 단순한 통합 인터페이스 제공
- **플라이웨이트(Flyweight)**: 다수의 작은 객체를 공유해 메모리 절약
- **프록시(Proxy)**: 대리 객체로 실제 객체 접근을 제어 (보안·캐싱·지연 로딩)

### 행위 패턴(Behavioral) — 객체 간 책임 분배·상호작용

- **옵저버(Observer)**: 객체 상태 변화 시 의존 객체들에게 자동 통지 (발행-구독)
- **전략(Strategy)**: 알고리즘군을 캡슐화해 실행 중 교체 가능
- **템플릿 메서드(Template Method)**: 알고리즘 골격은 상위 클래스, 세부 단계는 하위 클래스가 구현
- **상태(State)**: 객체 내부 상태에 따라 행위 변경
- **커맨드(Command)**: 요청을 객체로 캡슐화해 매개변수화·기록·취소 가능
- **책임 연쇄(Chain of Responsibility)**: 요청을 처리할 객체를 사슬로 연결, 차례로 전달
- **반복자(Iterator)**: 컬렉션 내부 구조 노출 없이 순차 접근
- **중재자(Mediator)**: 객체 간 직접 통신 대신 중재자를 통해 통신 (결합도 감소)
- **메멘토(Memento)**: 객체 상태를 저장·복원 (undo)
- **인터프리터(Interpreter)**: 언어 문법을 정의하고 해석
- **방문자(Visitor)**: 데이터 구조와 처리(연산)를 분리, 새 연산 추가 용이

	단골 출제: 싱글톤, 옵저버, 팩토리 메서드, 어댑터, 전략, 프록시의 "정의" 약술.
